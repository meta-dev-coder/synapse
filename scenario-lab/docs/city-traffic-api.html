City Traffic Simulation API

Denver, CO · Synapse Scenario Lab
v1.0 · FastAPI

Introduction

This API provides three city-scale traffic simulation scenarios for Denver, CO. Each scenario modifies the road network or signal plan, runs a traffic assignment model, and returns network-level and segment-level impact metrics — including a Cesium-compatible heatmap for visualization.

Calibration uses one month of real bus GPS data from bus_history.db combined with Denver Open Data (bus stops, bus routes, traffic signals). The road network is built from OpenStreetMap via OSMnx.

Base URL (local dev): http://localhost:8000
Base URL (production): routed through N8N webhook proxy — each endpoint has a corresponding /webhook/simulate-city-* path.

Data Sources

bus_history.db — RTD Bus GPS (Primary Calibration Input)

SQLite database containing one month of real-time GPS position broadcasts for all Denver RTD bus vehicles. This is the primary observational dataset used to calibrate per-segment traffic volumes and derive the origin-destination demand matrix. 

-- SQLite table schema
CREATE TABLE bus_positions (
    busId      TEXT,      -- RTD vehicle ID, e.g. "6088", "6102" — identifies individual buses
    bearing    REAL,      -- Compass heading 0–360° (0 = North, 90 = East)
                           -- Used for map-match direction validation: discard if
                           -- |GPS bearing − road bearing| > 45°
    lat        REAL,      -- WGS84 latitude  (Denver range: 39.61 – 39.81)
    lon        REAL,      -- WGS84 longitude (Denver range: -105.11 – -104.79)
    timestamp  INTEGER    -- Unix epoch in MILLISECONDS — divide by 1000 for seconds
                           -- e.g. 1706788412000 = 2024-02-01 08:13:32 UTC
);

Partial database corruption: The SQLite file has partial corruption beyond page 297,368. The pipeline reads in 100k-row chunks and stops at the first read error — all data before the corruption boundary is processed correctly. Approximately 5–10% of the final month of data may be missing.

What the GPS data is used for

Pipeline useHowOutput
Volume calibration Map-match each ping to nearest road edge. Count observations per edge. Scale by bus modal share (~6%) and observation hours to estimate total veh/hr. calibrated_volumes.json
OD matrix derivation Detect trip origins/destinations from per-bus position sequences. Assign to 500 m grid zones using 5-minute gap threshold between trips. od_matrix.json
Signal baseline GPS speed near each signalised intersection provides approach flow estimates for Webster optimal cycle calibration. signal_baseline.json

Known Limitations of bus_history.db

These limitations affect calibration accuracy when the pipeline is run. The demo network is not affected — it uses hand-tuned synthetic volumes.
#LimitationImpact
1 Buses only — no cars or trucks RTD buses represent roughly 5–8% of total Denver traffic. Car/truck volumes must be inferred using a fixed bus modal-share assumption (6%). Errors in this assumption propagate to all edge volumes. Highway edges (I-25, I-70) have very few bus observations and will rely almost entirely on synthetic HCM capacity estimates.
2 Partial corruption (last ~10% of data) Rows beyond page 297,368 are unreadable. This means the final portion of the capture period is absent. Volume calibration covers the readable window only; affected edges receive a synthetic fallback of 65% × capacity.
3 Variable ping interval GPS ping frequency varies from 10 to 90+ seconds depending on network congestion in the RTD AVL system. Computed speeds between distant pings are less reliable; these points are filtered by the 2–90 km/h speed plausibility check.
4 No time-of-day segmentation stored Timestamps are present but the pipeline aggregates all observations without separating AM/PM/off-peak windows during map-match. Peak scaling is applied analytically after the fact using the fixed PEAK_FACTORS constants (AM ×1.8 etc.), not from measured peak distributions.
5 Bearing accuracy at low speeds and turns GPS bearing is unreliable when a bus is nearly stationary (at stops, traffic lights) or executing turns. The 45° bearing-deviation filter discards these points. This means dwell time at stops is excluded from volume counts, which slightly underestimates congestion near busy stops.
6 No coverage of non-bus routes Streets with no RTD bus service (most residential collectors, some suburban arterials) have zero GPS observations. Their volumes fall back to 65% × HCM capacity (synthetic). Road-closure scenarios on these edges will produce less accurate spillover estimates.

HCM capacity defaults are assigned per highway type: motorway 2,200 · trunk 2,000 · primary 1,900 · secondary 1,800 · tertiary 1,700 · residential 1,200 veh/hr/lane. Free-flow speed is taken from OSM maxspeed tag, falling back to highway-type defaults when absent.

Data Pipeline

Run once offline. Outputs are committed to backend/app/data/city/ and loaded at server startup. All scripts live in backend/app/pipeline/.

1
fetch_denver_data.py — Download source data
Downloads the OSMnx road graph for the Denver bbox, fetches ArcGIS traffic signals (filtered to STATUS="IN USE" and SIGNAL_TYPE="Vehicular"), and downloads the RTD GTFS static feed to extract bus route IDs.
→ raw_graph.graphml, signals_raw.geojson, gtfs_routes.json
2
build_network.py — Build edges.json from OSMnx graph
Loads raw_graph.graphml, assigns stable edge IDs (u_v_k), applies HCM capacity defaults by highway type, assigns free-flow speed from maxspeed tag (falls back to highway defaults), and attaches RTD bus route IDs per edge from the GTFS feed. Loads calibrated_volumes.json from Step 3 if available; otherwise defaults to 65% × capacity.
→ edges.json
3
map_match_gps.py — Map-match bus GPS to road edges
Reads bus_history.db in 100k-row chunks (stops at page 297,368 to avoid corruption). For each GPS ping: snap to nearest OSMnx edge using ox.nearest_edges, validate bearing deviation (<45° threshold), discard points >50 m from road. Counts observations per edge, then scales to AM-peak veh/hr using bus modal share (6%) and observation hours (90 hr).
→ calibrated_volumes.json
4
build_od_matrix.py — Origin-Destination demand matrix
Streams bus positions ordered by (busId, timestamp). Detects individual trips using a 5-minute gap threshold. Maps each GPS ping to a 500 m × 500 m grid cell over the Denver bbox. Records origin cell (first ping) → destination cell (last ping) per trip. Scales trip counts to veh/hr using the same 90 hr / 6% modal share as Step 3.
→ od_matrix.json
5
build_signal_model.py — Signal timing baseline
Loads signals_raw.geojson (1,288 signals). For each signal, finds nearby calibrated edge volumes and applies Webster's optimal cycle formula (C = (1.5L + 5) / (1 − Y)) to compute baseline cycle lengths. Apportions green times proportionally by approach flow (NS vs EW). Falls back to 1,500 veh/hr approach volume when no GPS data is nearby.
→ signal_baseline.json

Simulation Engine

All three scenarios share the same traffic assignment library (city_assignment.py). The rerouting_model parameter selects between fast and accurate modes:

What is Simulated vs. Estimated

OutputHow it is computedConfidence
Congestion scalar (v/c) Directly from BPR using calibrated volumes and HCM capacity. Accurate when pipeline has been run. High (pipeline) / Medium (demo)
Travel time delta % Derived from BPR travel time change weighted by volume. Relative change is reliable; absolute value depends on volume calibration. Medium
Queue length (m) Computed as max(0, v − c) × 6.5 m/veh. Simplified; does not model shockwave propagation. Medium
Webster delay (signal timing) HCM 2000 formula applied to approach volumes. Accurate for pre-saturated conditions (x < 1.0). Less reliable at x > 0.9 (overflow regime). Medium–High
Rerouting fraction In demo mode: proportion of edges receiving redirected volume. In pipeline mode: fraction of OD pairs with changed shortest path. Indicative only (demo)
New link utilisation Capacity-weighted demand diversion model. Correct directionally; exact volumes depend on OD matrix quality. Indicative
Frank-Wolfe equilibrium (demo) In demo mode, FW is approximated by a 0.78 dampening factor on AoN flows — not a true iterative equilibrium. Run pipeline for full FW. Approximation (demo)

All-or-Nothing (AoN) — default fast mode

For every origin→destination pair in the demand matrix, all demand is routed along the single shortest path (Dijkstra). Fast; suitable for most planning decisions.

path = Dijkstra(G, origin, dest, weight=travel_time)
volume[e] += demand[od] for each edge e on path

Frank-Wolfe — accurate equilibrium mode

Iterative user-equilibrium assignment. Converges when total system travel time changes by less than 0.1% between iterations (typically 5–10 iterations).

k=1: AoN assignment → v⁰
k+1: compute t_e(v_e^k) via BPR
AoN on current costs → auxiliary flows y_e
λ* = argminλ∈[0,1] Σ ∫BPR via bisection
v_e^{k+1} = v_e^k + λ*(y_e − v_e^k)
stop when |TSTTk+1 − TSTTk| / TSTTk < 0.001

Scenario A — Road Closure

Simulates closure or partial capacity reduction of one or more road segments. Reassigns all traffic demand around the blockage and identifies spillover congestion zones.

POST /api/v1/simulate/city_road_closure
Close roads, reduce capacity, or simulate incidents. Returns network-wide travel time impact, spillover segment list, affected RTD routes, and per-edge heatmap.

Request Body

FieldTypeRequiredDescription
closures ClosedSegment[] required List of road closures (1–20). Each closure specifies one or more OSM edge IDs.
peak_period string optional "AM" (default) | "PM" | "OFF_PEAK". Scales OD demand by peak factor.
rerouting_model string optional "all_or_nothing" (default, fast) | "frank_wolfe" (accurate).
simulation_duration_sec integer optional 10–60 seconds. Controls UI progress animation pacing. Default: 30.

Shared Schemas

CityHeatmap

Returned by all three scenarios. Maps each road segment's OSM edge ID to a normalized congestion scalar (0.0 = free-flow, 1.0 = fully saturated). Used directly by the Cesium visualization layer to color road segments. 

{
  "edges": {
    "<edge_id>": 0.0  -- 1.0   (float, 0 = green, 1 = red)
  }
}

Formulas Reference

BPR Travel Time (Bureau of Public Roads)

Computes congested travel time from free-flow time and volume/capacity ratio. Used in all three scenarios.

t = tfree × ( 1 + 0.15 × (v / c)4 )

tfree = free-flow travel time (sec) — from GPS median speed
v = volume (veh/hr)
c = capacity (veh/hr)
congestion_scalar = min(v / c, 1.0)

Webster Delay (HCM 2000)

Intersection delay per vehicle at a signalized intersection. Used in Signal Timing scenario.

λ = g / C    green ratio
x = q / (s × λ)    degree of saturation; s = 1900 × lanes (pcphgpl)

d₁ = C × (1−λ)² / [ 2 × (1 − min(1,x) × λ) ]   uniform delay
d₂ = 900T × [ (x−1) + √((x−1)² + 8k·x / (c·T)) ]   T=0.25 hr, k=0.5
d = d₁ + d₂    seconds per vehicle

queue = q × d / 3600    vehicles

Frank-Wolfe Line Search (BPR integral)

Used to find the optimal step size λ* in the Frank-Wolfe assignment loop.

∫₀v BPR(x) dx = tfree × ( v + 0.15 × v⁵ / (5 × c⁴) )

λ* = argminλ∈[0,1] Σe ∫₀v_e+λ(y_e−v_e) BPRe(x) dx   via bisection

Peak Demand Scaling

demand_scaled = OD_demand × peak_factor

AM peak (06:00–09:00): factor = 1.8
PM peak (15:00–18:00): factor = 2.1
OFF_PEAK: factor = 0.6

Limitations

This section documents the known limitations of the current simulation system — covering both the demo network and the pipeline-calibrated network.

Data Limitations

LimitationDetailWorkaround / Roadmap
Bus-only GPS calibration bus_history.db contains only RTD bus positions. Buses account for ~6% of Denver vehicle trips. Car, truck, and LRT volumes are inferred using a fixed modal-share constant, not measured. Highway edges (I-25, I-70) have negligible bus coverage and rely entirely on HCM capacity models. Supplement with Denver DOT loop detector counts or HERE/TomTom speed data when available.
Static assignment (no time dynamics) All three scenarios use static traffic assignment — volumes represent a steady-state hourly average, not a dynamic within-hour progression. Queue build-up and dissipation over time are not modelled. Peak spreading effects are captured only through the AM/PM/OFF_PEAK demand multipliers. Dynamic traffic assignment (DTA) is deferred to a future version.
No turn penalties or intersection delay in assignment AoN and Frank-Wolfe assignment use edge travel times only. Turn-movement delays, prohibited turns, and intersection capacity are not modelled in the assignment step (they appear only in the Webster analysis for the signal scenario). Add turn-delay lookup table from GTFS shapes or Denver signal phase data.
Corrupt tail of bus_history.db The database has partial corruption beyond page 297,368, representing roughly the final 5–10% of the capture period. All affected rows are skipped. Edges with no GPS coverage in the readable window receive a synthetic volume of 65% × HCM capacity. Acquire a clean database export from the RTD AVL system for the same period.

Model Limitations

LimitationDetail
BPR α/β fixed at 0.15 / 4 The Bureau of Public Roads function uses standard coefficients (α = 0.15, β = 4). These are appropriate for US urban arterials but may under-predict congestion on narrow residential streets and over-predict it on modern limited-access highways. Calibrated coefficients per road class would improve accuracy.
Webster delay assumes under-saturation The HCM 2000 Webster model (d₁ + d₂) becomes unreliable when the degree of saturation x approaches or exceeds 1.0. At x > 0.95 the formula predicts infinite delay; the implementation caps x at 1.0 to produce finite outputs, but results above x = 0.90 should be interpreted as qualitative ("very high delay") rather than quantitative.
Frank-Wolfe approximation in demo mode When rerouting_model = "frank_wolfe" is selected and the pipeline has not been run, the service applies a fixed 0.78 dampening factor to AoN assignment results rather than running true iterative equilibrium. This approximation captures the general tendency of FW to distribute flows more evenly, but is not a convergence-guaranteed equilibrium solution. Run the pipeline to enable real Frank-Wolfe on the full 40k-edge network.
Demo network — 24 edges vs ~40k The built-in demo network covers only the 24 most significant Denver road segments. Scenarios affecting edges not in the demo set (residential streets, suburb arterials) will receive no output — only the 24 covered edges appear in responses. This is expected behaviour; run the pipeline for full network coverage.
Signal timing — two-phase model only The signal timing scenario models each intersection as a simple two-phase signal (NS green / EW green). Multi-phase signals with left-turn phases, protected-permissive movements, or pedestrian phases are reduced to an equivalent two-phase representation. Intersections with more than two competing movements will have less accurate delay and queue estimates.
New infrastructure — no geometric routing The new infrastructure scenario assigns demand to new links using a capacity-weighted gravity model rather than shortest-path routing from the specified from_node_id / to_node_id. The link geometry is not inserted into the graph. Utilisation figures are directionally correct but exact volumes require true graph-based assignment (available after pipeline run).

Scope Limitations

The following are explicitly out of scope for v1 and are documented here to set correct expectations for what the API does and does not model.
  • No freight or heavy vehicle weight classes — all traffic treated as passenger car equivalents
  • No transit ridership modelling — bus route disruptions affect road capacity only
  • No pedestrian or cycling network — drive edges only
  • No parking supply/demand interaction
  • No weather or incident probability modelling
  • No emissions output (unlike the toll-plaza module which includes CO₂/NOₓ)
  • No multi-day or seasonal variation — single peak-period snapshot

Error Handling

All errors return standard FastAPI HTTP responses:

StatusCauseExample
422 Pydantic validation failure capacity_reduction_pct outside [0,100], closures empty, invalid peak_period
500 Service error Unknown edge_id, unreachable OD pair, network disconnected after closure
If you close too many edges and the network becomes disconnected, some OD pairs will be unreachable. The service handles this gracefully — lost demand is reported separately, simulation continues with reachable pairs.

Timeout guidance

Set client timeout to at least simulation_duration_sec + 30 seconds. Frank-Wolfe with a dense OD matrix may take 20–60 seconds on the full Denver network. All-or-Nothing typically completes in 2–8 seconds.
